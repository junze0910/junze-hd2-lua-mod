# No Large Piercing —— Mod 介绍

> 分类：**优化类（Optimization）** ｜ 类型：Lua 注入型运行时内存补丁 ｜ 不修改任何游戏文件

## 一、为什么做这个

《绝地潜兵2》在弹丸命中目标时会播一个"命中特效档位"，由数据表字段 `HitEffectDamageType` 决定：

```
0 None            1 PiercingSmall      2 PiercingMedium    ★降到这里
3 PiercingLarge   ★                  4 PiercingLargeHEAT   ★
5 IncendiarySmall 6 IncendiaryMedium   7 BeamSmall         8 BeamLarge
9 Blunt           10 SlashingSmall     11 SlashingLarge    12 VehicleStep
13 PiercingSmallStim                   14~17 Unk
```

`3` / `4` 都是**大口径**档。它们在命中瞬间会产生明显更"重"的火花与碎片效果，在密集交火（尤其是一堆小口径武器同时开火）时观感偏吵、视觉干扰也更大。

本 mod 就做一件事：**把这两档从数据表里整体改写掉** —— 改成 `0`（`None`），完全不播大型穿刺特效。

* 曾有一个 `→ 2`（`PiercingMedium`）降档版 **No Large Piercing (Medium)**，**自 v1.5 起停止维护/发布**（源码还在，需要时自行用 `tools\build_mod.py no_large_piercing_medium` 打包）。

**只改视觉档位，不碰任何伤害数值、弹道、射速或穿透逻辑。**

## 三、原理

### 3.1 目标表与字段

两张设置表在内存里都是标准的 **LDLD 数据块**：

```
+0   "LDLD"     ← 魔数
+4   u32 版本 = 1
+8   u32 类型哈希 = djb2(类型名)      ProjectileSettings = 0xBD4042C2 / ExplosionSettings = 0x2AEA2592
+12  u32 数据区字节数
+24  16 B 数组描述符 { u64 记录起点偏移(=16), u64 条数 }
+32  u32 条数
+40  记录数组起点
```

| 表 | 元素类型 | 记录尺寸 | 目标字段偏移 |
|---|---|---:|---|
| `ProjectileSettings` | `ProjectileInfo` | 272 B | `+232` `effect_damage_type` |
| `ExplosionSettings` | `ExplosionInfo` | 152 B | `+76` `hit_effect_damage_type` |

两个字段的类型哈希都是 `0xB43002D3` = `djb2("HitEffectDamageType")`，且在各自结构体里**各只有一个**，所以"类型哈希 → 字段"是一一对应的。

### 3.2 运行时流程

0. **找表交给 HD2 Scanner（v1.6 首选）**：`ProjectileSettings` / `ExplosionSettings` 本来就在 Scanner 的已登记表里，它按「区段基址 +0x4 是不是 `LDLD` + 类型哈希」逐区段读 16 字节定位，urgent 一轮 ≈0.5 秒，广播出每份副本的 LDLD 地址；本 mod 只 `request()` + `declare_need()` + 对 `poll()` 出的地址走下面的 2~5 步，**自己不扫内存**。
   > 没装 Scanner（或 30 秒内广播不到这两张表）→ 回退到第 1 步那套自带扫描。
1. **时间切片扫描内存**（回退路径；启动后第 120 帧 ≈2 s 开始）：按 `LDLD + 版本(1) + 类型哈希` 三件套定位两张表。
   一次性模式下整轮用 1 MB 块 / 每帧 10 ms 预算（实机整轮 ≈23 s，两张表在第 1381 帧写完）；块间只保留 7 字节「缝」防止数据表横跨块边界被整张漏掉。
2. **定位记录区**：优先用数组描述符里的 `u64` 起点偏移；若运行时被重定位成绝对指针，则改用该指针；两种都拿不到时退回固定 `+40`。用"前若干条记录的 `type` 是否落在合理值域"来裁决选哪个。
3. **内容自洽校验**（详见 §四）。
4. **逐条写入**：对每条命中记录，`VirtualProtect` 临时放开只读页 → 写 4 字节 → 恢复原保护属性。
5. **整块回读逐条复核**：不信 `WriteProcessMemory` 的返回值，重新读出整段记录区，逐条确认目标字段已等于目标值；不符则记日志并放弃。
6. **写完就停（v1.5/v1.6）**：两张表都写入并复核通过后，再只读复核一遍全部 108 个地址，然后**彻底停止扫描** —— 没有维护窗口、没有热区自检、没有兜底全量。装了 Scanner 时还要继续听它广播：新地址（换图后的新副本）出现就自动补写。
   > 唯一的常驻动作是「金丝雀」：每 60 秒只读这 108 个 4 字节地址（432 字节/分钟）。被写回 `3`/`4` 就补写；地址失效就退回维护式调度（`ONE_SHOT = false` 的那套：复查 + 热区自检 + 兜底全量）。
   > 表在内存里可能有多份副本；一次性模式**只打它找到的那一份**（多份副本的场景请用 `ONE_SHOT = false`）。

### 3.3 安全设计

* 任何一项校验不通过 → **只记日志、绝不写入**；
* 写入前把原始字节与"目标清单"dump 到日志目录（可追溯、可复现）；
* 用 `_G` 单例守卫防止重复加载；两个变体用同一个互斥键，**同时启用时后者自动退出**；
* 全流程 `pcall` 包裹，单点失败不会拖垮扫描；
* 一次性模式带 **3 分钟超时**（`ONE_SHOT_DEADLINE`）：没找齐两张表就记日志并退回维护式调度，不会一直满预算扫下去。

## 四、踩过的坑：为什么不能用「记录下标」当指纹

第一版把 `{下标, 枚举值}` 当指纹（比如"下标 0 应该是 `ProjectileType 282`"）。实机时**被拒写**：

```
ProjectileSettings @0x...：基线指纹不符（记录 0 期望 282/228，实为 286/234）
```

排查过程值得记下来：

1. 一开始误判成"官方在枚举中间插入了新项、编号整体顺延"（因为 `282→286`、`228→234` 看起来像顺延）；
2. 用**玩家自己从游戏内提取的 ID 表**交叉验证后推翻了这个结论 —— 镜像里的 343 个 `ProjectileType` 有 **306 个仍原样存在于新版表里**，说明**编号根本没顺延**；
3. 真正的差异是：官方在**末尾追加**了新编号（弹头 `344..350` 共 7 个、爆炸 `416/417/420/422`），同时**把记录在表里的排列顺序重排了**。

结论：**记录下标是版本相关的易变量，不能当指纹**。改为只检查"内容应该长什么样"：

* 全部 `type` / 关联伤害 ID ≤ 4095（枚举值域）
* 全部特效字段 ≤ 31
* 不同 `type` 值的数量 ≥ 条数的 50%

记录尺寸或字段偏移一旦变化，这几条会**同时崩掉**，照样拦得住；而顺序变化则完全不受影响。

另外，**条数**也不该要求严格相等：离线镜像（`filediver` 的 `datalibrary`）可能比游戏旧（镜像 343 / 413 条，实测游戏 350 / 422 条）。现在只要求"不少于校验所需"，并把实际条数与镜像条数一起打进日志便于核对。

## 五、数据来源与验证

| 项 | 来源 |
|---|---|
| 字段偏移 / 记录尺寸 | 游戏自带 **typelib**（经 `filediver` 的 `datalibrary` 导出，1177 个类型的成员偏移） |
| 字段语义 / 枚举名 | [Helldivers2_RawData](https://github.com/Darctor/Helldivers2_RawData) 的 `Data/enums/HitEffectDamageType.txt` 等枚举名表 |
| 条目名称 | 游戏内提取的 ID 表（`弹头ID` / `爆炸ID` / `伤害ID`） |

偏移与尺寸用**明文数据表逐条比对**验证：

```
ProjectileSettings   343 条 × 6 字段   → 0 处不符
ExplosionSettings    413 条 × 8 字段   → 0 处不符
```

实机验证（2026-09-25）：两张表均 `已回读验证通过`，`3` / `4` 档计数归零。

## 六、兼容性

* 验证环境：Helldivers 2、Bingus Shared Loader **v16（API 1）**
* 不依赖版本相关的固定条数或记录下标，同大版本内的小更新一般无需改动
* 游戏若改动数据表结构（记录尺寸 / 字段位移），addon 会**拒写并留下日志**，不会乱写
* **v1.6 的找表**依赖 HD2 Scanner（core 线）；没有它时回退自带一次性扫描（`ONE_SHOT`）
* **回退路径的取舍**：金丝雀只能发现「原地址上的值被写回」；表若被换到**新地址**（新副本），回退路径看不到 —— 手动调 `_G.HD2_NoLargePiercing_Rescan()` 或改用 `ONE_SHOT = false`（Scanner 路径没有这个问题）
