# AC-8 机炮背包替换 mod —— v6 设计说明（内容锚点法）

* 目标：把战备 **AC-8 机炮**包架上的背包，从 `0xE60AE045E0090F4C`（16576307969206587212）
  换成 `0x26BDDF070C31B275`（2791632565401924213）。
* 对象：内存里的运行时数据表 `HellpodRackComponentData`（LDLD 块，类型哈希 `0xA98BB156`）。
* 依据：`double_leveller.lua`（荡平 mod）的做法 + skill 案例
  `hd2-build-update-repair-案例.md` §1。
* 本文只讲**怎么定位、怎么判断、怎么保证不写错**，不含代码。

---

## 1. 一句话结论

> **只认签名，不认布局；目标字段靠"内容"定位，靠"上下文"确认。**

表怎么长、索引多少条、记录多大、目标在第几条 —— 这些**构建相关的数字一个都不用**。

---

## 2. 为什么要重写：v5 失效的根因

v5 的定位方式是「**表结构指纹 + 记录下标**」，写死了 4 个数：

| v5 常量 | 含义 | 更新后会不会变 |
|---|---|---|
| `EXPECT_SIZE = 42568` | 表声明大小 | **会变** |
| `INDEX_COUNT = 140` | 索引区条数 | **会变** |
| `NONZERO_INDEX = 70` | 非空索引条数 | **会变** |
| `TARGET_REC = 4` | 目标记录下标 | **会变**（前面插一条就全体后移） |

任一不符，v5 就**拒绝写入**（安全，但等于什么都不做）。所以在更新后的版本里：

* 现象 = "装上没效果"，连日志里也只有一行 `declared size=... 与预期 ... 不符，拒绝写入`；
* 这不是 bug，是**闸门太紧**：它把"版本变了"和"找错地方了"当成同一件事。

skill 给的修法原话：**闸门只留 `LDLD + 版本 + 类型哈希`**。

## 3. 运行时数据表长什么样（LDLD 块）

```
+0     'LDLD'
+4     u32 version = 1
+8     u32 typeHash        djb2(类型名)，HellpodRackComponentData = 0xA98BB156
+12    u32 size            数据区字节数（不含 24 字节表头）
+16    u8  is64 + 7 pad
+24    数据区：
         ComponentIndexData[Ni]      每条 16 字节 (u64 实体哈希, u32 记录下标, u32 pad)
         <记录区>                     Nr 条 × 记录步长
```

**稳定性分级（这是整个设计的地基）：**

| 字段 | 版本间是否稳定 | v6 是否使用 |
|---|---|---|
| `'LDLD'` 魔数 | 稳定 | ✅ 用来定位 |
| `version = 1` | 稳定 | ✅ 用来校验 |
| `typeHash` | 稳定（djb2 类型名，除非箭头改类型名） | ✅ 用来定位 |
| `size` | 不稳定 | ⚠️ 只做 1KB~4MB 的合理区间检查 |
| `Ni / Nr / 步长` | 不稳定 | ❌ 完全不用 |
| 记录下标 | 不稳定 | ❌ 完全不用 |
| **记录内容**（物品哈希 / 节点哈希） | **稳定**（是游戏数据本身） | ✅ **靠它定位** |

## 4. AC-8 包架记录的实测布局（旧版明文镜像，rec 4）

一条 `HellpodRackComponent` = 8 × `RackAttach[64]` + 尾部字段：

```
RackAttach: +0 u64 Item / +8 u32 Node / +12 Vec3 Offset / +24 Vec3 Rot /
            +36 +40 +44 三个 u32 事件 / +48 u8 / +52 RackSide(u32) / +56 u8
```

AC-8 记录实测（`AC-8 = 武器+背包` 型战备，左右各一份）：

| 槽位 | 偏移 | Item | Node | RackSide |
|---|---|---|---|---|
| s0 | +0 | `0xA8CFFB316F0B5C5F` 机炮本体 | `0x76C6D1E3` | 2 (Left) |
| **s1** | **+64** | **`0xE60AE045E0090F4C` 旧背包** | `0xEE08A75F` | 1 (Right) |
| s2 | +128 | `0xA8CFFB316F0B5C5F` 机炮本体 | `0x76C6D1E3` | 2 (Left) |
| **s3** | **+192** | **`0xE60AE045E0090F4C` 旧背包** | `0xEE08A75F` | 1 (Right) |
| s4~s7 | +256… | 0（空槽） | `0xE89D1227` | 0 |
| 尾部 | +556 | `SpawnPayloadSize = 2` | | |

两点关键实测结论：

1. **旧背包哈希在整张表里只出现 2 次**，且都在这一条记录里（s1 与 s3）→ 天然唯一锚点。
2. **s1 与 s3 必须一起改**，否则包架上一边新、一边旧。
3. 机炮本体哈希 `A8CFFB316F0B5C5F` 在同一记录里也出现 2 次（s0/s2）→ 可用来做"上下文确认"。

## 5. v6 定位算法

### 5.1 找表（签名）

扫内存，对每个 `LDLD` 命中点读 24 字节表头，四条全过才算：

```
head[0..3]  == 'LDLD'
u32(head, 4)  == 1
u32(head, 8)  == 0xA98BB156      ← HellpodRackComponentData
1024 <= u32(head,12) <= 4194304  ← 只做合理区间，不当指纹
```

### 5.2 找字段（内容 + 上下文）

在**已确认的表**的数据区（`magic+24`，最多读 256KB）里搜 8 字节：

```
for 每个 "旧背包哈希" 的命中点 at:
    for cand in {64, 192}:                      ← s1 / s3 相对记录起点的偏移
        rec = at - cand
        if 0 <= rec and data[rec..rec+8] == 机炮本体哈希 then
            → 命中点确认属于 AC-8 包架记录，可写 at
            break
    else
        → 只记日志，跳过（别的包架 / 别的表里的同款哈希，不动）
```

**为什么这样就够用**：

* `at - 64`/`at - 192` 是**记录内部**的相对偏移 —— 属于"内容布局"，跨版本稳定；
* 不需要知道记录区从哪开始、步长多少、这是第几条；
* 上下文用的是"同一条记录里另一格的物品哈希"，比"记录下标/表大小"稳得多。

### 5.3 幂等（已打过补丁怎么认）

同一套流程再跑一遍，搜的是 **新背包哈希**：

* 命中 + 上下文校验通过 → 记为 `already`（已是目标状态，不重复写）；
* 因此 mod 被装两次、或游戏重载表后自动重打，都不会写坏。

## 6. 写入与校验

```
$old = VirtualProtect(page, PAGE_READWRITE)      -- 表所在页可能是只读
WriteProcessMemory(at, 新背包 8 字节)
VirtualProtect(page, $old)                        -- 恢复原属性
back = ReadProcessMemory(at, 8)
assert back == 新背包哈希                          -- 回读校验，失败则计入 refusals
```

* **只改这 8 字节**，记录其余 560 字节逐字节保持原样；
* 一次一轮里**所有命中的槽位都写**（s1 + s3）；
* 写失败 / 回读不符 → 只记日志，不重试乱写。

---

## 7. 扫描策略：多副本 + 轻量复查（照抄荡平的工程学）

1. **一轮内扫到几张表副本就全打**：绝不能"命中第一个就收工"。
   游戏可能同时持有同一张表的多份副本，只改一份 = 游戏照样读没改的那份
   （skill 6.17，且和扫描顺序有关 → 表现为"能用一阵子然后突然失效"）。
2. **自我命中规避**：锚点字节串活在 Lua 堆里，扫描必然命中自己 →
   开扫前先取自身字符串地址，命中点落在其 ±4KB 内就跳过。
3. **帧预算**：每帧最多 2ms 扫描、256KB 分块 + 2KB 重叠，避免掉帧。
4. **复查**：每 5 秒对每个已写地址只读 8 字节（微秒级）。
   * 还是新哈希 → 存活；
   * 变回旧哈希 → 立刻重写；
   * 读不到 / 变成别的 → 丢弃该地址；全部丢弃则回到全量扫描。
5. **退避与放弃**：空轮 2/4/8/16/30/60/120/300 秒退避，连续 8 轮空手就放弃扫描，
   留一份 census 供离线分析（避免无限空扫浪费帧）。
6. **落盘**：
   * `AC8RackBackpack.log` —— 主日志（每条立即落盘，loader 的 `open_log` 是 `w` 模式）；
   * `Census.log` —— 内存里所有 LDLD 类型清单（诊断用：表到底加载了没）；
   * `AC8RackBackpack_Status.log` —— 一行状态摘要（OK / WORKING / FAILED + 计数）。

---

## 8. 安全红线

1. 任何一步校验不过 → **只写日志，绝不落笔**；
2. 只按内容锚点 + 上下文确认后写入，绝不"按偏移硬写"；
3. 所有大于 2^53 的哈希一律用"十六进制文本 → 字节串"构造，**绝不过 Lua number**（浮点精度会吃掉低位）；
4. 不修改磁盘文件，只在运行时改内存（游戏重启即回到原状态）。

## 9. 与 v5 的差异对照

| | v5 | v6 |
|---|---|---|
| 表定位 | 签名 + `size == 42568` | 签名 + size 区间检查 |
| 记录定位 | 索引区扫实体哈希 → 记录下标必须 == 4 | 表数据里搜旧背包哈希 + 上下文校验 |
| 依赖常量 | 大小 / 索引条数 / 非空数 / 记录下标 | 只有类型哈希 + 记录内相对偏移 |
| 多副本 | 命中第一个就 `done` 收工 | 一轮内全部副本都打 |
| 复查 | 只复查一个地址 | 逐地址轻量复查，掉一个补一个 |
| 空扫 | 无退避，一直扫 | 指数退避 + 8 轮放弃 + census |
| 版本更新后 | 静默拒写（无效果） | 内容不变就照常生效 |

1. **本文的实测数据来自 9/21 版明文镜像**（`filediver-src/datalibrary/generated_entities.dl_bin`，45.6MB）。
   游戏在 **9/24 18:27 又更新了一次**，且新版的 `data/game/generated_entities.dl_bin`（46.6MB）与
   `dl_library.dl_typelib` **已加密/压缩**（整块高熵、扫不到 `LDLD`、搜不到明文类型名）→
   **离线无法再核对**，只能靠运行时探针（`mount_probe`）验证。
2. 若新版本把背包物品哈希或记录内布局改了，v6 会**拒写并留下可诊断日志**（不是乱写）；
   届时按日志里的 census / 上下文不符信息重新定锚点即可。
3. 本 mod 只改 AC-8 包架；同一张表里若有**别的包架**也用同一个背包哈希，
   会被上下文校验挡掉（日志里会记 `foreign` 计数）。
4. 传感器 mod 那条待定项（44 字节基线在表里命中 **10** 条，而护卫犬只有 7 条）

## 12. v6.1 增补（前置升级到 v16 之后）

### 12.1 环境闸门（SKILL 6.18）
loader 版本不够时 addon **照样会被加载、照样会跑**，只是安静地做不成事 ——
用户看到的是"一直 working"，真正的原因永远不会出现在日志里。
v16 会在 `_G.CowboyBingusModLoader` 里放 `{ api = 1, version = 16, modules = {} }`，所以 v6.1 开头先问一句：

* 读到 `api < 1` → 写 STATUS.txt 第一行，然后 **直接 return（不扫描、不写内存）**；
* 读不到这个 global → **不拒绝**（将来可能有别的 loader），退化去解析
  `BingusSharedLoader.log` 首行 `loader-v(\d+); API (\d+)`；
* 版本号一律写进 STATUS.txt，让每张支持工单自带环境信息。

### 12.2 STATUS.txt（SKILL 6.16 / 6.19）
文件 `AC8RackBackpack_STATUS.txt`：**第一行就是结论**（`OK - 补丁生效中（N 处）` /
`WORKING - 扫描中` / `FAILED - ...`），下面才是细节（前置版本、内存里的表副本数、已写/拒绝计数、轮次）。
日志是给开发者看的，状态文件是给用户看的。

### 12.3 维护扫描 + 全量兜底（SKILL 6.17）
同类型 LDLD 块在内存里有几十份，而且**进任务 / 换图时会再加载一份新的**。
"只打第一份" = 一开始生效、过一会儿失效，而复查还会说一切正常。v6.1 因此分三层：

| 周期 | 动作 | 代价 |
|---|---|---|
| 5 秒 | 逐地址复查（每个地址只读 8 字节）；被冲掉就重打，读不到就丢弃 | 微秒级 |
| 30 秒 | 扫「已知表副本地址 ±32KB」合并出的观察窗口（几 MB），抓新加载的副本 | 比全地址空间便宜两个数量级 |
| 10 分钟 | 全量重扫兜底（副本万一被搬到别处） | 一次性，可接受 |

### 12.4 离线仿真器（SKILL 6.20）
用游戏自带的 `bin/lua51.dll`（LuaJIT，与实机同款）+ 假内存 + 假 loader 跑完整状态机，
在没有游戏的情况下验证：环境闸门 → 扫描 → 命中 → 写入 → 回读 → 复查 → 维护扫描 → 幂等。
之所以必须用游戏同款 Lua：别的版本会让 `//` 之类的 5.3 语法一路穿到实机才炸。

**仿真结果（5000 帧）**：
```
第 1 轮扫描开始：1 个可读区域
已替换：表 0x10002000 size=42568 记录(下标提示 4, SpawnPayloadSize=2) 槽位 +64，本轮写了 2 处
第 1 轮完成：命中（累计写入 2 处）
维护扫描：观察窗口 1 个，内存里表副本 1 处（本轮命中 1）   ← 识别为"已是目标状态"，不重复写
STATUS.txt 第一行 = OK - 补丁生效中（2 处）
槽位 +64 / +192 = 75B2310C07DFBD26（新背包）；+0 与 Node 一字未动 ✓
```
